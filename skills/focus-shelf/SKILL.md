name: focus-shelf
description: Explicit local Focus Shelf manual refresh.
---

Use only when the user explicitly requests an authorized manual Focus Shelf refresh. This thin Skill does not grant external account access or publish anything remotely.

The application, not ad-hoc Skill formatting, owns grouping. Preserve each ticket's current read-only Linear status: Backlog belongs to Backlog, and triage/unstarted to Upcoming. A Done/completed family belongs to Completed only when none of its verified associated PRs are still GitHub-open, regardless of PR author. If any such PR is open, keep the family in Current work while the ticket itself still visibly says Done; move it back to Completed after all those PRs are verified Merged or Closed. Never use a manually selected PR status to declare the family complete. A nested family stays together under its root card; each child keeps its own visible Linear state. The Slack In Progress report includes only tickets currently assigned to the configured owner and actually started in Linear, not creator-only or delegated work. Canceled and Duplicate tickets remain excluded from the working view, Archive and report, regardless of assignee. Keep verified duplicate relationships in source records, but do not create a second visible card. A duplicate link alone does not authorize adding an out-of-scope original to the owner's snapshot or transferring PR ownership.

After a verified refresh, the application removes an archived root family from Archive and shows it in Completed only when the root and every visible descendant are Done, PR discovery is complete for each ticket, and no associated PR remains GitHub-open. An incomplete or unavailable PR search never triggers automatic restoration. The snapshot writer itself does not edit Archive; the local page reconciles its external `archive.json` on reload.

Sprint is a separate time annotation, not completion evidence. Names such as `26.9.S1` mean year 2026, month 9, first Sprint; S2 is the second Sprint. Do not hardcode the example month, Sprint number, or a mid-month boundary. Collect actual Linear start/end dates, and let the application compare them with the viewer's current time (not the snapshot creation date) to label This/Upcoming/Past Sprint. A Sprint may span months. Without authoritative dates, keep the neutral Sprint label; do not guess whether today belongs to S1 or S2 from its name alone.

Required capability: an already authorized Linear connector/MCP that reads the configured owner's assigned issues, created-by-owner issues with verified `createdById`, prior created and followed IDs, reciprocal relations, Sprint metadata, estimate points and issue creation timestamps in the configured workspace. A first real home has config only and no prior snapshot; do not copy demo snapshot/catalog data into it. Ask for an explicit first refresh and create data only from verified account evidence. If complete Linear coverage is unavailable, preserve the previous files or retain an empty first home and report the gap.

Optional catalog enrichment: an authorized GitHub connector/MCP or logged-in CLI that reads verified associated PR metadata and complete checks/status. Confirm issue association, repository, PR number, base branch, GitHub open/merged/closed state, current Draft flag and observed head; keep passed/failed/pending/skipped/neutral/unknown distinct. Keep the check named exactly `Release target policy` out of the ordinary CI passed/failed/pending totals; count its failures in optional `releaseTargetPolicyFailed`: it produces an attention triangle, while only actual test, build or lint failures produce a red cross. Skipped checks are not failures. Without optional GitHub coverage, preserve existing catalog files; a stale time binding may safely hide them. Never invent PR/check observations.

For each refreshed open PR, also read GitHub's mergeability at the observation time. Store `mergeability:'conflicting'|'mergeable'|'unknown'` only when verified; absence in an older catalog means unavailable, not conflict-free. A confirmed merge conflict keeps the GitHub lifecycle Open and shows a separate accessible `×` even when checks pass. It is not a CI failure. Open and Ready for Review remain selectable local annotations; only GitHub Merged or Closed locks the selector. A second same-profile browser window may be read-only because another window holds the writer lock; selecting a status there requests the lock and reports failure without saving if it remains unavailable. Do not bypass the lock.

For each PR, keep GitHub lifecycle and Focus Shelf workflow distinct. `merged` and `closed` are authoritative terminal states. An existing open PR starts as Open even when Draft, checks are absent, pending or failed. Mark it Ready for Review automatically only when the current GitHub observation proves `isDraft:false`, CI coverage is complete for the exact current head, at least one required check passed, and no non-skipped test/build/lint check failed, remains pending, neutral or unknown. Ignore skipped checks for readiness. A failure of the check named exactly `Release target policy` does not block Ready for Review; show an attention triangle instead. Missing Draft or current-head CI evidence must not be treated as a pass. Collect `isDraft` on every newly refreshed open PR; older catalogs without that field stay readable but cannot establish automatic readiness. On each verified PR refresh, advance that PR's `observedAt` to the new observation time even if its GitHub lifecycle is unchanged. Preserve manual selections across refreshes; if the user chose Merged or Closed while GitHub remains Open, show a mismatch reminder instead of erasing the choice.

Also inspect the latest effective GitHub Changes requested review, not merely the aggregate `reviewDecision` string or PR `updatedAt`. Record its reviewed `commitSha` and `submittedAt` in optional `review:{decision:'changes-requested',commitSha,submittedAt}`. For each open PR, collect the actual completion time of its current-head non-policy checks; after all required checks are complete and green, store the latest completion time as optional `ciObservations[].completedAt`. Ready for Review depends on current-head Draft and CI evidence as above, not on the reviewDecision string. If the latest Changes requested time is newer than the last full-green CI completion, show a `↻ Changes requested` attention badge beside Ready for Review; if the full-green CI completed later, hide that badge. Missing CI completion time cannot prove the review was superseded, so keep the badge. A CI rerun after review does not itself prove code changed; verify the head/commit history separately before claiming changes addressed the review. A later approval supersedes the request. If review chronology is uncertain, report the uncertainty rather than inventing times. A daily PR refresh rechecks every known open PR, not just the one named in a prior conversation.

A user may instead request only `update PR #N` or `update all known PRs`. This is a catalog-only refresh against the existing validated Linear snapshot: read the named PR or every PR already in the catalog, verify current GitHub lifecycle, mergeability, Draft, latest effective review versus current head, and current-head CI for open PRs; preserve associations, unrelated catalog evidence, Memo and Archive. Keep `snapshotGeneratedAt` bound to the unchanged snapshot, update only refreshed PR observations and affected CI/coverage, then publish through the catalog writer after validation and continuity checks. Do not re-read all Linear issues, claim new PR discovery, or call it a full Focus Shelf update. If the ticket association, owner, snapshot binding or Linear scope is uncertain, preserve the prior files and use the regular daily/full refresh instead. Short natural-language requests invoke these same rules; the long button prompt is not a prerequisite.

Keep credentials in the authorized connector or logged-in CLI session; never write credentials into config, snapshots, catalog, DRI data or browser overlays. The starter neither installs capabilities nor signs in to accounts. New real setups use this checkout's ignored `.focus-shelf/` data home by default and create only a profile config before an authorized refresh; `FOCUS_SHELF_HOME` may explicitly select a different absolute directory, including an existing installation. Do not move or overwrite existing personal data automatically. Demo setup uses synthetic examples in a separate home. The shared repository's `config/team-dri.json` is the common reviewed Domain/Workstream/First DRI/Second DRI map; a deliberate `FOCUS_SHELF_TEAM_HOME` may override it locally. Never infer DRI from the Linear assignee or copy profile identity, email, employee IDs, ticket data, personal notes or credentials into the shared map or this Skill.

Distinguish a restricted execution/network error from invalid account credentials. If a CLI authentication check fails inside a restricted sandbox, perform a permitted read-only connectivity/authentication check through the host's normal approval mechanism before declaring GitHub unavailable. Never bypass policy, expose tokens, or sign the user out. A successful Git push alone does not establish API access to each required company repository.

Before attributing a GitHub login to the configured person, obtain explicit user confirmation or authoritative identity evidence. Similar usernames, an issue link and the merge actor do not bind a person to a GitHub account. Ask once when the mapping is unresolved, continue complete Linear/presentation collection, and keep affected PR responsibility unverified until evidence or the user's answer resolves it. Never put real account mappings into the shared repository.

1. Read the starter's CODEX_SNAPSHOT.md and `config.json` in the resolved data home (default `.focus-shelf/`, or explicit `FOCUS_SHELF_HOME`). Confirm the requested profile, owner and workspace; do not use personal defaults.
2. On an empty home, do the complete initial collection: assigned and created-by-owner seeds, then recursively collect the complete reciprocal child closure. For later daily updates, use the last successfully published `snapshot.generatedAt` as the cursor. Query all Linear issues updated since 24 hours before that timestamp, exhaust pagination, and also enumerate the owner's current assigned issue IDs and issues created since the overlap window. Retain all previously published created/followed seeds, including Done items. Merge verified changed records into the prior complete set; do not rebuild from only the delta. Refresh current Sprint membership for every retained issue on every daily update, including issues previously having no Sprint; a ticket may be added to, removed from, or moved between Sprints independently of the other fields being reviewed. Refresh Sprint name and authoritative dates for every detected change. If complete membership coverage for the retained issue set is unavailable, preserve the previous files and report the gap instead of publishing Sprint data that may be stale. Refresh the full reciprocal child closure for every new/changed seed and any parent whose relationships changed, including externally assigned, unassigned and Done children. A ticket created by the configured owner remains eligible after reassignment; verify creator membership from `createdById`. Remove records only when evidence proves they are outside assigned/created/followed membership and all retained child closures. Do not expand external parent/related/blockedBy tickets. Exhaust pagination for every changed issue's children. Preserve unaffected records and project all in-set edges. If the last snapshot/cursor is missing, identity changes, delta queries fail, relation closure is incomplete, or scope drift cannot be reconciled, preserve the prior files and run/report a full reconciliation instead of publishing a partial delta. Use a full refresh on explicit request or suspected drift. Classification precedence is assigned, created, followed, then context. More than 1,000 final issues prevents publication.
3. Before concluding that a new/changed ticket has no prior identity, relation or PR, inspect its Linear comments through the authorized connector. Extract only referenced issue identifiers, explicit relationship wording and exact GitHub PR URLs; do not retain raw comment bodies. Distinguish explicit parent/child, duplicate, dependency and implementation-PR statements from contextual mentions, and verify each claimed relationship against current Linear/GitHub metadata. Resolve a historical Linear identifier as an alias only when looking up that old identifier returns the current identifier with the same stable UUID and compatible creation evidence. If it returns a different UUID, it is a separate ticket. A verified alias may bridge a PR that names the historical identifier to the current ticket; title similarity or an unverified comment mention cannot.

   Keep association and responsibility separate. The Linear assignee owns the ticket, and parent/child nesting never transfers that ownership. Record a PR author only as its creator, a GitHub assignee as explicit PR responsibility, a review request as review duty, and the merger as the merge actor. Do not attribute a PR to the profile owner merely because it is linked to a parent, child, related ticket or shared workstream. Keep another owner's child ticket as delegated context. Display all verified PRs associated with a visible ticket family, but label each PR created by someone other than the profile owner as `Created by <verified first name or GitHub login>`; never imply that association makes it the profile owner's PR. Verify the creator's GitHub login and the profile-owner comparison for each newly refreshed PR. A friendly name requires explicit user confirmation or authoritative identity evidence; otherwise use the GitHub login.

4. Build the strict allowlisted schema v2 candidate outside the repository (`scope:'assigned-created-followed-context'` with `createdIssueIds`; see `buildSnapshotV2`). Never include issue descriptions, comments, attachments, customer data, credentials, raw service responses or error bodies. Match ticket identifiers exactly: DEMO-2 is not DEMO-20. Collect each issue's verified Linear `createdAt` as a canonical ISO timestamp. Never substitute updated/completed dates or infer creation from its identifier. The application groups Completed families by Sprint (newest first), otherwise by the root ticket's creation month in the configured timezone; all subgroups start collapsed. Missing legacy creation dates remain Undated. Add the current verified Linear estimate as an optional integer or explicit null; omission means it was not collected. Never infer points, days or effort, and do not display a placeholder for null/omitted values. Optional catalog must use the same schema and snapshot timestamp. Each PR has verified current headSha and per-ticket association `{kind:'linear-attachment'|'github-reference',issueId,sourceUrl}` with the exact issue or GitHub PR URL binding described in CODEX_SNAPSHOT.md. A direct PR URL found in a comment is discovery evidence only unless the current schema's accepted association proof is also satisfied; otherwise keep it as an unresolved candidate outside the published catalog. Do not infer associations from substring matches. Include exactly one coverage entry per snapshot issue; mark GitHub/CI gaps unavailable, never infer no-PR from an incomplete search. CI conclusions require complete per-ticket coverage and repository + PR number + current head match. Keep older snapshots readable but never downgrade an existing v2 snapshot. For each visible parent ticket or shared-topic family, invoke the bundled `generate-focus-shelf-icon` Skill with only the verified title and a short sanitized task summary. Store its validated `{version:1,paths:[...]}` result in `presentation.tickets[].icon`; reuse it while the ticket meaning is unchanged. The Focus Shelf application owns the large, consistent flat 2D SVG rendering. Never emit Emoji, raw SVG/HTML, text, URLs, embedded images or executable markup. When the ticket's verified scope matches an entry in the shared/configured DRI map, add that exact `workstream`; otherwise omit it and report the gap. Do not hardcode known ticket IDs, guess ownership, or infer completion/status from an illustration. Use the neutral `ticket` key for uncertain topics.
   Every successful real snapshot refresh must publish a presentation catalog bound to that same new timestamp. For a delta, preserve verified associations, catalog details and observations for unaffected tickets; refresh discovery for changed/new ticket trees, and refresh all previously open PRs plus newly discovered PRs at their current heads. Preserve every previous verified PR association unless evidence establishes a correction. Give each newly visible root an evidence-aligned topic thumbnail and preserve existing icons while meaning is unchanged. Missing GitHub or CI access does not remove thumbnails: mark affected per-ticket PR/CI coverage unavailable and keep validated prior evidence where still applicable. Reconcile against the prior repository + PR number set; never bypass the continuity guard for incomplete discovery. If the delta cannot safely retain unaffected entries or reconcile the full resulting pair, preserve the previous snapshot. Use the catalog writer only; never write `catalog.json` directly.
5. Run `node scripts/write-codex-snapshot.mjs INPUT.json` with the correct resolved data home. Set `FOCUS_SHELF_HOME` only for a deliberate override; the default is this checkout's ignored `.focus-shelf/`. Respect lock contention and reread latest evidence before retrying.

   Before either writer runs, calculate top-level cards from the final `buildSnapshotV2` projection, not raw Linear `parentId`. A ticket whose parent is outside the selected scope becomes a visible top-level card. Check that every such card has a validated presentation icon; a raw-parent count must not cause those icons to disappear. Validate the complete snapshot/catalog pair before publishing either file.
6. Verify the running starter's actual local origin and report publication evidence separately from rendered-page verification. Normal setup uses `http://localhost:8770`. Do not stop an existing service or change an existing profile's origin. For an explicitly requested isolated colleague trial, use a separate data home and the exported `startServer({home,port})` API with a separate port; keep that origin stable for the trial. The top `Update` button copies the complete refresh request for the user to paste into Codex; it never contacts Linear/GitHub or claims synchronization. Memo, manual PR status and Archive are stored in the resolved local data home and shared by browsers using the same server. Existing browser-only Archive entries are imported when that browser opens the page if the shared Archive file does not yet exist. Each manual PR selection persists across later observations. A later verified PR refresh keeps the chosen label and flags Merged or Closed when GitHub still reports Open; once GitHub confirms Merged or Closed, the verified terminal state takes precedence without deleting the local record. An open GitHub PR alone cannot establish review readiness; current Draft and current-head CI evidence support automatic classification, while the local manual selection remains a separate user annotation. A refreshed observed GitHub `merged` or `closed` state is authoritative even if the local choice differs. Ticket status remains separate read-only Linear evidence and changes only through a later verified snapshot refresh. Preserve actual assignees for every child: another owner's nested child work is collapsed by the application, while a creator-owned ticket reassigned to someone else remains a first-class row labelled `Created → Assigned to <first name>`. A created ticket with no assignee displays only `Unassigned`; this does not assign it to its creator. Neutral topic tones render in the application's default blue, independent of Upcoming/Backlog grouping; only On Hold mutes the thumbnail. The internal assigned/created/followed/context classification otherwise stays out of each visible Assignee line.

Setup: Node 22+, `.focus-shelf/config.json` in the ignored default data home, `npm start`; `FOCUS_SHELF_HOME` is optional for an existing or separate absolute directory. Normal startup serves localhost:8770; an isolated trial may use the explicit server API as described above. Each server accepts only its actual localhost origin. Opening/editing/reloading never reads Linear/GitHub. Memo and Archive require the local server; editing still requires a valid profile and Web Locks, so a second same-origin window is read-only. Archive and manual PR status are saved in the local data home. Ticket status is displayed from the current Linear snapshot and is never locally selectable. Without complete external evidence, preserve existing files. Remote publication, sharing, deployment, migration and messages require separate authorization.
