name: focus-shelf
description: Explicit local Focus Shelf manual refresh.
---

Use only when the user explicitly requests an authorized manual Focus Shelf refresh. This thin Skill does not grant external account access or publish anything remotely.

Required capability: an already authorized Linear connector/MCP that reads the configured owner's assigned issues, created-by-owner issues with verified `createdById`, prior created and followed IDs, reciprocal relations, Sprint metadata and estimate points in the configured workspace. A first real home has config only and no prior snapshot; do not copy demo snapshot/catalog data into it. Ask for an explicit first refresh and create data only from verified account evidence. If complete Linear coverage is unavailable, preserve the previous files or retain an empty first home and report the gap.

Optional catalog enrichment: an authorized GitHub connector/MCP or logged-in CLI that reads verified associated PR metadata and complete checks/status. Confirm issue association, repository, PR number, base branch, state and observed head; keep passed/failed/pending/skipped/neutral/unknown distinct. Count a check named exactly `Release target policy` in optional `releaseTargetPolicyFailed`, not generic `failed`: it produces an attention triangle, while only actual test, build or lint failures produce a red cross. Skipped checks are not failures. Without optional GitHub coverage, preserve existing catalog files; a stale time binding may safely hide them. Never invent PR/check observations.

Keep credentials in the authorized connector or logged-in CLI session; never write credentials into config, snapshots, catalog, DRI data or browser overlays. The starter neither installs capabilities nor signs in to accounts. Demo setup uses synthetic examples in a separate external home; real setup creates only config before an authorized refresh. An optional private external `dri.json` stores an authorized, fixed-version Domain/Workstream/First DRI/Second DRI map. Never infer DRI from the Linear assignee, and never copy real names into this Skill or the shareable repository.

Distinguish a restricted execution/network error from invalid account credentials. If a CLI authentication check fails inside a restricted sandbox, perform a permitted read-only connectivity/authentication check through the host's normal approval mechanism before declaring GitHub unavailable. Never bypass policy, expose tokens, or sign the user out. A successful Git push alone does not establish API access to each required company repository.

Before attributing a GitHub login to the configured person, obtain explicit user confirmation or authoritative identity evidence. Similar usernames, an issue link and the merge actor do not bind a person to a GitHub account. Ask once when the mapping is unresolved, continue complete Linear/presentation collection, and keep affected PR responsibility unverified until evidence or the user's answer resolves it. Never put real account mappings into the shared repository.

1. Read the starter's CODEX_SNAPSHOT.md and external FOCUS_SHELF_HOME/config.json. Confirm the requested profile, owner and workspace; do not use personal defaults.
2. Through already authorized capabilities, obtain complete assigned, created-by-owner and followed seeds, retaining prior created and followed IDs including Done items. A ticket created by the configured owner remains eligible after reassignment; verify this only from Linear `createdById`, not comments, history text or familiarity. Exhaust all pagination and recursively collect the complete reciprocal child closure at every depth, including externally assigned, unassigned and Done children. Do not expand external parent/related/blockedBy tickets. Project only relations with both endpoints in the final set, retaining all in-set edges. Classification precedence is assigned, created, followed, then context. Permissions, incomplete pagination/relations or more than 1,000 final issues prevent publication: preserve the prior snapshot and explain the gap.
3. Before concluding that a new/changed ticket has no prior identity, relation or PR, inspect its Linear comments through the authorized connector. Extract only referenced issue identifiers, explicit relationship wording and exact GitHub PR URLs; do not retain raw comment bodies. Distinguish explicit parent/child, duplicate, dependency and implementation-PR statements from contextual mentions, and verify each claimed relationship against current Linear/GitHub metadata. Resolve a historical Linear identifier as an alias only when looking up that old identifier returns the current identifier with the same stable UUID and compatible creation evidence. If it returns a different UUID, it is a separate ticket. A verified alias may bridge a PR that names the historical identifier to the current ticket; title similarity or an unverified comment mention cannot.

   Keep association and responsibility separate. The Linear assignee owns the ticket, and parent/child nesting never transfers that ownership. Record a PR author only as its creator, a GitHub assignee as explicit PR responsibility, a review request as review duty, and the merger as the merge actor. Do not attribute a PR to the profile owner merely because it is linked to a parent, child, related ticket or shared workstream. Keep another owner's child ticket as delegated context, but omit that person's PR rows from the current profile. A PR on another owner's ticket may appear only when current GitHub assignment or explicit task evidence proves it belongs to the profile owner and the active catalog schema supports that proof. Unknown responsibility stays unknown and is not displayed as profile-owned work.

4. Build the strict allowlisted schema v2 candidate outside the repository (`scope:'assigned-created-followed-context'` with `createdIssueIds`; see `buildSnapshotV2`). Never include issue descriptions, comments, attachments, customer data, credentials, raw service responses or error bodies. Match ticket identifiers exactly: DEMO-2 is not DEMO-20. Add the current verified Linear estimate as an optional integer or explicit null; omission means it was not collected. Never infer points, days or effort, and do not display a placeholder for null/omitted values. Optional catalog must use the same schema and snapshot timestamp. Each PR has verified current headSha and per-ticket association `{kind:'linear-attachment'|'github-reference',issueId,sourceUrl}` with the exact issue or GitHub PR URL binding described in CODEX_SNAPSHOT.md. A direct PR URL found in a comment is discovery evidence only unless the current schema's accepted association proof is also satisfied; otherwise keep it as an unresolved candidate outside the published catalog. Do not infer associations from substring matches. Include exactly one coverage entry per snapshot issue; mark GitHub/CI gaps unavailable, never infer no-PR from an incomplete search. CI conclusions require complete per-ticket coverage and repository + PR number + current head match. Keep older snapshots readable but never downgrade an existing v2 snapshot. For each visible parent ticket or shared-topic family, invoke the bundled `generate-focus-shelf-icon` Skill with only the verified title and a short sanitized task summary. Store its validated `{version:1,paths:[...]}` result in `presentation.tickets[].icon`; reuse it while the ticket meaning is unchanged. The Focus Shelf application owns the large, consistent flat 2D SVG rendering. Never emit Emoji, raw SVG/HTML, text, URLs, embedded images or executable markup. When the ticket's verified scope matches an entry in the private DRI map, add that exact `workstream`; otherwise omit it and report the gap. Do not hardcode known ticket IDs, guess ownership, or infer completion/status from an illustration. Use the neutral `ticket` key for uncertain topics.
   Every successful real snapshot refresh must publish a presentation catalog bound to that same new timestamp. Give every visible top-level ticket card or shared-topic family one evidence-aligned topic thumbnail; grouped children reuse the parent thumbnail rather than duplicating it. Missing GitHub or CI access does not remove thumbnails: publish per-ticket PR/CI coverage as unavailable and keep the validated presentation section. Reconcile the candidate against the previously published repository + PR number set before publication. The application writer rejects silent PR disappearance; do not bypass it because discovery was incomplete. Use `--allow-pr-removal OWNER/REPO#NUMBER` only for an individually verified ownership or association correction and record why that exact PR is intentionally removed. If the presentation section or PR reconciliation cannot be regenerated safely, preserve the prior snapshot rather than publishing a new timestamp that would hide existing catalog evidence. Use the catalog writer only; never write `catalog.json` directly.
5. Run `node scripts/write-codex-snapshot.mjs INPUT.json` with the correct FOCUS_SHELF_HOME. Destination is fixed and external; respect lock contention and reread latest evidence before retrying.

   Before either writer runs, calculate top-level cards from the final `buildSnapshotV2` projection, not raw Linear `parentId`. A ticket whose parent is outside the selected scope becomes a visible top-level card. Check that every such card has a validated presentation icon; a raw-parent count must not cause those icons to disappear. Validate the complete snapshot/catalog pair before publishing either file.
6. Verify the running starter's actual local origin and report publication evidence separately from rendered-page verification. Normal setup uses `http://localhost:8770`. Do not stop an existing service or change an existing profile's origin. For an explicitly requested isolated colleague trial, use a separate external home and the exported `startServer({home,port})` API with a separate port; keep that origin stable for the trial. The top `Update` button copies the complete refresh request for the user to paste into Codex; it never contacts Linear/GitHub or claims synchronization. Memo, Archive and non-terminal manual PR status are browser-local and remain unchanged by refresh. An open GitHub PR cannot establish review intent, so the user sets Ready for Review manually. A refreshed observed GitHub `merged` or `closed` state is authoritative and the application displays it over an older local Open/Ready selection. Ticket status remains separate read-only Linear evidence and changes only through a later verified snapshot refresh. Preserve actual assignees for every child: another owner's nested child work is collapsed by the application, while a creator-owned ticket reassigned to someone else remains a first-class row labelled `Created → Assigned to <first name>`. The internal assigned/created/followed/context classification otherwise stays out of each visible Assignee line.

Setup: Node 22+, external FOCUS_SHELF_HOME, `npm start`. Normal startup serves localhost:8770; an isolated trial may use the explicit server API as described above. Each server accepts only its actual localhost origin. Opening/editing/reloading never reads Linear/GitHub. Browser-local overlays require a valid identity and Web Locks; a second same-profile window is read-only. Ticket status is displayed from the current Linear snapshot and is never locally selectable. Without complete external evidence, preserve existing files. Remote publication, sharing, deployment, migration and messages require separate authorization.
