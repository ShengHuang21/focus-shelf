# Explicit local snapshot contract

This procedure requires an explicit user request and existing authorization to read the relevant external workspace. Opening or editing Focus Shelf never invokes it. No credentials, descriptions, comments, attachments, customer payloads, raw responses or error bodies belong in a snapshot.

Read the external `FOCUS_SHELF_HOME/config.json`. Confirm profile identity, Linear owner and workspace. Collect all assigned, created-by-owner and followed seeds, retaining previously created and followed IDs including completed issues, then recursively fetch their entire reciprocal child hierarchy to arbitrary depth. A created ticket remains eligible after it is reassigned; prove creator membership from Linear `createdById`, never from comments, history text or familiarity. Include externally assigned, unassigned and Done descendants. Pagination must be exhausted for seed queries and every child collection; permission gaps, unresolved relations, incomplete pages or a final set exceeding 1,000 issues prevent publication. Preserve the existing snapshot and report the gap. Do not substitute an active-only search. Do not silently drop a created or followed issue.

Only root fields `schemaVersion`, `generatedAt`, `source`, `scope`, `ownerId`, `createdIssueIds`, `followedIssueIds`, `issues` are accepted for a new refresh. New refreshes use schema 2, canonical ISO timestamps, `source:{kind:'codex-manual-refresh',workspaceSlug}`, and `scope:'assigned-created-followed-context'`. Each issue contains only `id`, `uuid`, `title`, `url`, `status:{name,type}`, `assignee:{id,name}|null`, `relations:[{type,issueId}]`, `sprint:{name,startDate,endDate}|null`, and optional `estimate:<integer>|null`. Maximum 1,000 issues. URLs must match the configured Linear workspace and exact issue ID (DEMO-2 never matches DEMO-20). Parent/child relations must be reciprocal, acyclic and have at most one parent. Other unknown fields fail validation. A verified estimate integer is displayed as a numbered circle; explicit `null` means Linear has no estimate, while omission means a legacy/uncollected field. Neither case displays a placeholder, and Focus Shelf never infers or edits estimate points. Earlier schema-2 snapshots without `createdIssueIds` and with `scope:'assigned-followed-context'` remain readable, but every newly collected candidate must include the creator seed set.

The v2 set is exactly the union of complete assigned/created/followed seeds and their reciprocal child closure. Classification precedence is assigned, then created, then followed, then context. A created ticket currently assigned to another person is rendered as `Created → Assigned to <first name>` and remains a first-class ticket rather than delegated context. External parents, related and blockedBy tickets never expand the set. Project relations to retain every edge whose two endpoints are in the final set; do not drop in-set child edges. `buildSnapshotV2` in `lib/snapshot.mjs` constructs this projection from a complete collection and rejects unresolved child evidence. The validator can verify the submitted graph but cannot prove an external connector exhausted its pages or included an unreported child; the collector must establish that evidence before publication. Publication also refuses to silently lose any previously recorded created seed. Legacy v1 assigned/followed and earlier v2 assigned/followed/context snapshots remain readable; v2 publication cannot fall back to v1.

Accepted Linear status types are `triage`, `backlog`, `unstarted`, `started`, `completed`, `canceled`, and `duplicate`. Preserve `duplicate` and its original display name; never rewrite it as completed/canceled evidence. The UI gives it a gray badge and places terminal duplicate work in the collapsed Completed group, unless an owned open PR keeps delivery active. Accepted relation types are `parent`, `child`, `blockedBy`, `blocks`, `related`, and `duplicateOf`. `blocks` and `duplicateOf` retain their direction and only appear when both endpoints are already in scope; they do not expand the selected set or create child nesting.

Write candidate input outside the repository, then run `node scripts/write-codex-snapshot.mjs INPUT.json` with the intended `FOCUS_SHELF_HOME`. The CLI accepts only input; destination is fixed. Publication acquires an exclusive external lock, rereads the latest state, validates, checks rollback/completeness, writes and syncs a temporary file, then atomically renames. Exact repeats return `unchanged`. Lock contention returns `SNAPSHOT_LOCKED`: wait for the owning writer, then retry from newly read evidence. Do not remove an unexplained stale lock automatically; diagnose ownership first. A failure after rename may already have published the new snapshot; inspect the destination before retrying.

Catalog is optional. Its strict fields are demonstrated in the synthetic example and validator. Bind schema, owner, workspace and `snapshotGeneratedAt` exactly: v1 pairs only with v1, v2 only with v2. Catalog never accepts scripts, arbitrary presentation markup or raw service payloads. A ticket presentation may carry one verified `workstream` label. When a private external `dri.json` has the exact same workstream, the page shows First and Second DRI separately from Linear assignee. Do not infer DRI from assignee or publish the real ownership map. GitHub or CI gaps do not prevent a complete Linear snapshot; publish v2 coverage as unavailable, or retain a previous catalog whose stale binding will hide it. PR/CI data is observational; skipped/neutral/unknown checks are distinct from passed checks. Store failures from a check named exactly `Release target policy` in optional `releaseTargetPolicyFailed`, not generic `failed`: they render as an attention triangle, while `failed` is reserved for actual test, build or lint failures that render a red cross. Manual browser PR status is local user annotation.

Catalog publication has a PR continuity guard. If a previously published repository + PR number is still attached to an issue in the current snapshot, a replacement catalog may update or move that PR to another verified ticket but may not silently remove it. The writer fails with `PR_CONTINUITY_INCOMPLETE` before replacing the file. A verified ownership/association correction may explicitly acknowledge each intended removal with `--allow-pr-removal OWNER/REPO#NUMBER`; unused acknowledgements fail, so this is not a blanket bypass. Record the evidence for that correction and never use the option merely because GitHub access was incomplete.

Every v2 PR adds `headSha` (40 hex characters) and `association:{kind,issueId,sourceUrl}`. `kind` is only `linear-attachment` or `github-reference`; association issueId must equal the PR entry issueId. Verify the exact ticket identifier in attachment/reference evidence, never a substring or title inference. A linear-attachment source URL must bind the exact configured workspace/issue; a github-reference source URL must equal that entry's exact `https://github.com/OWNER/REPO/pull/NUMBER` URL. PR and source URLs reject nonempty ports, query strings and fragments. Do not store attachment bodies or PR descriptions. PR entries are unique by repository + number + issueId; one PR may be associated with several tickets only with separately verified evidence for each. Such entries must have identical repository, number, URL, baseBranch, state, purpose, observedAt and headSha; only issueId and association may differ.

Top-level `coverage` has exactly one `{issueId,pr,ci,observedAt}` entry for every snapshot issue. `pr` is `complete|unavailable`; `ci` is `complete|unavailable|not-applicable`. No PR is an established observation only when pr=complete. Use ci=not-applicable only with complete PR collection and zero associated PRs; incomplete discovery uses unavailable. CI observations are unique by repository + number + headSha. The UI shows a CI conclusion only when that ticket's ci coverage is complete and the observation matches the PR repository, number and current headSha; all mismatches or missing evidence remain unknown. A green check on an older head is never current proof.

Partial discovery may retain individually verified PR rows while setting that ticket's `pr` and `ci` coverage to `unavailable`. An unreadable additional candidate must not erase verified PRs or be counted as complete discovery. With `pr=unavailable`, `ci` must also be unavailable even if checks for some known rows were read successfully.

Ticket topic illustrations are generated during the authorized refresh, not keyed to known ticket IDs. For each visible parent ticket or shared-topic family whose verified title and brief task context support a useful recognition aid, invoke the bundled `generate-focus-shelf-icon` Skill and add one `presentation.tickets` entry with exactly `issueId`, a short `label`, one validated `icon`, one allowlisted `tone`, and an evidence-aligned `description`. New icons use `{version:1,paths:[...]}` in the fixed `0 0 64 64` coordinate system. Each of 1–12 paths contains only a bounded SVG `d`, role `stroke|fill|accent|inverse`, and optional strokeWidth 1–6. The application owns the large, consistent flat 2D rendering; the Skill chooses and draws a stable topic metaphor from current task meaning. Raw SVG/HTML, Emoji, text, transforms, CSS, URLs, scripts, embedded images, customer content and delivery-status claims are rejected. Existing allowlisted string keys remain readable for compatibility, and legacy plain-text `glyph` catalogs use the neutral vector fallback. If the topic is unclear, use the built-in `ticket` key rather than inventing meaning.

Verify the local page and report what was collected, published or preserved. Snapshot refresh never changes browser-local memos, archive flags or manual PR status. No remote write, sending, deployment, sharing or migration is authorized by this procedure.
