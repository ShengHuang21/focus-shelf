# Explicit local snapshot contract

Use the common reviewed First/Second DRI map at `config/team-dri.json` for every profile unless `FOCUS_SHELF_TEAM_HOME` explicitly provides a local team override. Preserve blank assignments. Only assign an exact workstream to a ticket using verified capability/scope evidence, never the ticket assignee or title keywords alone. A refresh must not rewrite the map or replace it with historical personal defaults. The shared map may contain team workstream names and DRI names only; never put per-profile identity, email, employee ID, personal notes, ticket payloads or credentials in it.

This procedure requires an explicit user request and existing authorization to read the relevant external workspace. Opening or editing Focus Shelf never invokes it. No credentials, descriptions, comments, attachments, customer payloads, raw responses or error bodies belong in a snapshot.

Read the external `FOCUS_SHELF_HOME/config.json`. Confirm profile identity, Linear owner and workspace. Collect all assigned, created-by-owner and followed seeds, retaining previously created and followed IDs including completed issues, then recursively fetch their entire reciprocal child hierarchy to arbitrary depth. A created ticket remains eligible after it is reassigned; prove creator membership from Linear `createdById`, never from comments, history text or familiarity. Include externally assigned, unassigned and Done descendants. Pagination must be exhausted for seed queries and every child collection; permission gaps, unresolved relations, incomplete pages or a final set exceeding 1,000 issues prevent publication. Preserve the existing snapshot and report the gap. Do not substitute an active-only search. Do not silently drop a created or followed issue.

Only root fields `schemaVersion`, `generatedAt`, `source`, `scope`, `ownerId`, `createdIssueIds`, `followedIssueIds`, `issues` are accepted for a new refresh. New refreshes use schema 2, canonical ISO timestamps, `source:{kind:'codex-manual-refresh',workspaceSlug}`, and `scope:'assigned-created-followed-context'`. Each issue contains only `id`, `uuid`, `title`, `url`, `status:{name,type}`, `assignee:{id,name}|null`, `relations:[{type,issueId}]`, `sprint:{name,startDate,endDate}|null`, and optional `estimate:<integer>|null` and `createdAt:<canonical ISO timestamp>`. Collect verified Linear creation dates for newly refreshed issues; legacy omission remains readable. Completed families use Sprint first (newest first), otherwise the root's creation month in the configured timezone. Missing creation dates remain Undated; never substitute updated/completed dates. All Completed subgroups are collapsed by default. Maximum 1,000 issues. URLs must match the configured Linear workspace and exact issue ID (DEMO-2 never matches DEMO-20). Parent/child relations must be reciprocal, acyclic and have at most one parent. Other unknown fields fail validation. A verified estimate integer is displayed as a numbered circle; explicit `null` means Linear has no estimate, while omission means a legacy/uncollected field. Neither case displays a placeholder, and Focus Shelf never infers or edits estimate points. Earlier schema-2 snapshots without `createdIssueIds` and with `scope:'assigned-followed-context'` remain readable, but every newly collected candidate must include the creator seed set.

The v2 set is exactly the union of complete assigned/created/followed seeds and their reciprocal child closure. The first refresh must collect that entire scope. A daily refresh may collect a delta and merge it into the previous complete snapshot: use the last successful `generatedAt` as a cursor, query Linear `updatedAt` from 24 hours before it, exhaust pages, enumerate the current assigned IDs and newly created issues, and retain all prior created/followed seeds. Also re-verify current Sprint membership for every retained issue on every daily refresh, including those previously without a Sprint; tickets may be added to, removed from, or moved between Sprints over time. Refresh authoritative Sprint names and dates when membership changes. If complete Sprint-membership coverage is unavailable, preserve the old pair and report the gap rather than publishing potentially stale Sprint data. Refresh the complete reciprocal child closure of changed/new seeds and affected parents. Preserve unchanged issue records and all unaffected catalog evidence. The new timestamp marks the merged pair; it does not mean every preserved observation was re-read. If the cursor is absent, identity changes, delta pages/closure fail, or unexplained scope drift appears, preserve the old pair and run a full reconciliation. Use full refresh when explicitly requested or when results suggest drift. Classification precedence is assigned, then created, then followed, then context. A created ticket currently assigned to another person is rendered as `Created → Assigned to <first name>` and remains first-class. External parents, related and blockedBy tickets never expand the set. Retain all in-set edges. `buildSnapshotV2` validates a complete merged collection and rejects unresolved child evidence. Publication refuses to silently lose prior created seeds. Legacy v1 and earlier v2 snapshots remain readable; v2 cannot fall back to v1.

Accepted Linear status types are `triage`, `backlog`, `unstarted`, `started`, `completed`, `canceled`, and `duplicate`. Preserve `duplicate` and its original display name; never rewrite it as completed/canceled evidence. The UI omits Canceled and Duplicate cards from the shelf, Archive and report while retaining their source records. Ticket status always remains read-only Linear evidence. For shelf placement only, a completed root family with any verified associated GitHub-open PR on the family stays in Current work; after all such PRs are verified merged or closed, it belongs to Completed. Manual PR-status selections cannot make that move. Accepted relation types are `parent`, `child`, `blockedBy`, `blocks`, `related`, and `duplicateOf`. `blocks` and `duplicateOf` retain their direction and only appear when both endpoints are already in scope; they do not expand the selected set or create child nesting.

Write candidate input outside the repository, then run `node scripts/write-codex-snapshot.mjs INPUT.json` with the intended `FOCUS_SHELF_HOME`. The CLI accepts only input; destination is fixed. Publication acquires an exclusive external lock, rereads the latest state, validates, checks rollback/completeness, writes and syncs a temporary file, then atomically renames. Exact repeats return `unchanged`. Lock contention returns `SNAPSHOT_LOCKED`: wait for the owning writer, then retry from newly read evidence. Do not remove an unexplained stale lock automatically; diagnose ownership first. A failure after rename may already have published the new snapshot; inspect the destination before retrying.

Catalog is optional. Its strict fields are demonstrated in the synthetic example and validator. Bind schema, owner, workspace and `snapshotGeneratedAt` exactly: v1 pairs only with v1, v2 only with v2. Catalog never accepts scripts, arbitrary presentation markup or raw service payloads. A ticket presentation may carry one verified `workstream` label. When the shared or configured team DRI map has the exact same workstream, the page shows First and Second DRI separately from Linear assignee. Do not infer DRI from assignee or copy profile-specific/private data into the shared map. GitHub or CI gaps do not prevent a complete Linear snapshot; publish v2 coverage as unavailable, or retain a previous catalog whose stale binding will hide it. PR/CI data is observational; skipped/neutral/unknown checks are distinct from passed checks. Exclude the check named exactly `Release target policy` from ordinary CI `passed` and `failed` totals; store its failures in optional `releaseTargetPolicyFailed`: they render as an attention triangle, while `failed` is reserved for actual test, build or lint failures that render a red cross. Manual Open/Ready for Review/Merged/Closed PR status is a user annotation in the external local `pr-status.json`. Keep it across observations; if a manual Merged or Closed choice conflicts with GitHub Open, show a mismatch reminder. Verified GitHub Merged or Closed remains authoritative.

Catalog publication has a PR continuity guard. If a previously published repository + PR number is still attached to an issue in the current snapshot, a replacement catalog may update or move that PR to another verified ticket but may not silently remove it. The writer fails with `PR_CONTINUITY_INCOMPLETE` before replacing the file. A verified ownership/association correction may explicitly acknowledge each intended removal with `--allow-pr-removal OWNER/REPO#NUMBER`; unused acknowledgements fail, so this is not a blanket bypass. Record the evidence for that correction and never use the option merely because GitHub access was incomplete.

A PR-only refresh may replace the catalog without recollecting Linear when the existing snapshot binding, owner, association and PR set remain valid. Recheck the requested known PRs (or all known PRs), preserve unrelated catalog evidence, keep the same `snapshotGeneratedAt`, and publish only through the catalog writer after validation and continuity checks. This does not claim that Linear scope, Sprint membership or newly associated PRs were refreshed.

Every v2 PR adds `headSha` (40 hex characters) and `association:{kind,issueId,sourceUrl}`. `kind` is only `linear-attachment` or `github-reference`; association issueId must equal the PR entry issueId. Verify the exact ticket identifier in attachment/reference evidence, never a substring or title inference. A linear-attachment source URL must bind the exact configured workspace/issue; a github-reference source URL must equal that entry's exact `https://github.com/OWNER/REPO/pull/NUMBER` URL. PR and source URLs reject nonempty ports, query strings and fragments. Do not store attachment bodies or PR descriptions. PR entries are unique by repository + number + issueId; one PR may be associated with several tickets only with separately verified evidence for each. Such entries must have identical repository, number, URL, baseBranch, state, purpose, observedAt and headSha; only issueId and association may differ.

Every newly refreshed open PR must include GitHub's current boolean `isDraft`; legacy v2 catalogs may omit it and remain readable. Keep `state:'open'` as GitHub's not-yet-merged lifecycle, not as a claim about review readiness. The page may derive Ready for Review only from `isDraft:false`, complete CI coverage at the exact current head, at least one passed non-policy check, and zero failed/pending/neutral/unknown non-policy checks. Skipped checks do not block readiness. `Release target policy` failure remains a triangle and does not block readiness. Missing Draft or CI evidence leaves the automatic state Open. GitHub merged/closed states override all non-terminal annotations.

For a refreshed open PR, record GitHub mergeability as optional `mergeability:'mergeable'|'conflicting'|'unknown'` at the same `observedAt`. Omit it when not checked; omission is not proof of mergeability. A verified `conflicting` value displays an accessible `×` beside the PR while its GitHub lifecycle stays Open. Merge conflict is separate from CI, test/build/lint failure and from the local Open/Ready for Review selector. An Open PR selector remains available; selecting in a read-only window first requests the writer lock and reports failure without saving if the lock remains unavailable. Only GitHub Merged or Closed disables that selector by lifecycle.

For each newly refreshed PR, record a verified optional `creator:{login,displayName,isProfileOwner}` in the local catalog. `login` is GitHub's PR author; `displayName` is a confirmed first name or the login itself; `isProfileOwner` is determined only from a confirmed GitHub identity for this shelf. This is creator attribution, not assignment or review duty. The page shows `Created by ...` for non-owner PRs associated with the ticket, while still counting every verified associated PR for family completion. Keep these real account mappings only in the external local catalog, never in the shared repository example or team DRI configuration.

An open PR may additionally contain `review:{decision:'changes-requested',commitSha,submittedAt}` from the latest effective GitHub Changes requested review. A CI observation may contain `completedAt`, the latest completion time of its fully green, current-head non-policy check set; skipped checks and Release target policy do not block it. Ready for Review is determined by Draft and current-head CI, independent of GitHub's aggregate reviewDecision. Show `↻ Changes requested` beside that state only when the request was submitted after the last fully green CI completion. A later fully green CI hides the badge, including when GitHub still reports CHANGES_REQUESTED. Missing CI completion evidence cannot prove the request was superseded. A CI rerun after review is not itself evidence of a code change; verify head history separately before claiming the requested modification was made.

Top-level `coverage` has exactly one `{issueId,pr,ci,observedAt}` entry for every snapshot issue. `pr` is `complete|unavailable`; `ci` is `complete|unavailable|not-applicable`. No PR is an established observation only when pr=complete. Use ci=not-applicable only with complete PR collection and zero associated PRs; incomplete discovery uses unavailable. CI observations are unique by repository + number + headSha. The UI shows a CI conclusion only when that ticket's ci coverage is complete and the observation matches the PR repository, number and current headSha; all mismatches or missing evidence remain unknown. A green check on an older head is never current proof.

Partial discovery may retain individually verified PR rows while setting that ticket's `pr` and `ci` coverage to `unavailable`. An unreadable additional candidate must not erase verified PRs or be counted as complete discovery. With `pr=unavailable`, `ci` must also be unavailable even if checks for some known rows were read successfully.

Ticket topic illustrations are generated during the authorized refresh, not keyed to known ticket IDs. For each visible parent ticket or shared-topic family whose verified title and brief task context support a useful recognition aid, invoke the bundled `generate-focus-shelf-icon` Skill and add one `presentation.tickets` entry with exactly `issueId`, a short `label`, one validated `icon`, one allowlisted `tone`, and an evidence-aligned `description`. New icons use `{version:1,paths:[...]}` in the fixed `0 0 64 64` coordinate system. Each of 1–12 paths contains only a bounded SVG `d`, role `stroke|fill|accent|inverse`, and optional strokeWidth 1–6. The application owns the large, consistent flat 2D rendering; the Skill chooses and draws a stable topic metaphor from current task meaning. Raw SVG/HTML, Emoji, text, transforms, CSS, URLs, scripts, embedded images, customer content and delivery-status claims are rejected. Existing allowlisted string keys remain readable for compatibility, and legacy plain-text `glyph` catalogs use the neutral vector fallback. If the topic is unclear, use the built-in `ticket` key rather than inventing meaning.

Verify the local page and report what was collected, published or preserved. Snapshot refresh never changes the local Memo or PR-status files or browser-local Archive; a newer PR observation leaves the manual selection intact while the page warns if manual Merged or Closed conflicts with verified GitHub Open. No remote write, sending, deployment, sharing or migration is authorized by this procedure.
